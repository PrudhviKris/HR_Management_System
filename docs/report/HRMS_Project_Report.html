HRMS: How It Was Built and How It Works

Human Resource Management System · FastAPI + MySQL backend · React frontend · JWT + role-based access

1. What the system does

HRMS lets a company manage employees, attendance, leave, payroll and salary slips from one web app. There are three roles: Admin (everything), HR (people operations) and Employee (self-service). Each role sees only the menus and data it is allowed to.

3. How I built it (step by step)

  1. Designed the database: 24 tables (users, roles, employees, attendance, leave, payroll, payslips, audit logs ...) as SQLAlchemy models, then generated the MySQL schema with an Alembic migration.
  2. Built security first: login with bcrypt-hashed passwords, JWT tokens, and a permission system (25 permissions grouped into roles).
  3. Wrote the business logic as services: employees, attendance, leave, payroll, notifications, reports and audit.
  4. Exposed it as REST APIs: each module has a router under /api/v1/..., and each route declares the permission it needs.
  5. Built the React frontend: login page, a role-based sidebar, an admin panel and an employee panel.
  6. Added seed data, tests and deliverables: a demo dataset, 29 automated API tests, a Postman collection, a DB dump, screenshots and a sample payslip.

4. Architecture: how a request travels

→

→
Routerchecks token + permission, validates input
→

→
SQLAlchemysaves to MySQL in one transaction

The answer comes back as JSON, and React Query stores it and refreshes the screen. Backend folders follow the same layers: routers/ (URLs) → services/ (logic) → models/ (tables), with schemas/ for request/response shapes.

Example: employee clicks "Check in"
Frontend: CheckInWidget calls POST /api/v1/attendance/check-in with the token.
Backend: the router confirms the user is logged in and has attendance:self. attendance_service.check_in() rejects a second check-in for the same day (the database also has a unique rule: one row per employee per day), saves the time, marks the employee late if after 9:45, and writes an audit entry.
Result: the widget switches to "Check out", and at check-out the worked hours are calculated automatically.

5. Login and security: how it works

  1. The user logs in with email + password. The backend compares against the bcrypt hash; plain passwords are never stored.
  2. The backend returns a short-lived access token (JWT, 30 min) and sets a refresh token in a secure HttpOnly cookie that JavaScript cannot read.
  3. The frontend keeps the access token in memory only and sends it on every request as Authorization: Bearer <token>.
  4. When the token expires, the frontend silently calls /auth/refresh to get a new one, so the user stays logged in. Logout or a password change revokes all sessions.
  5. Every API checks a permission (for example payroll:process). Admin can create roles and tick permissions in the UI, and changes apply immediately.
  6. Extra protection: 5 wrong passwords lock the account for 15 minutes; inputs are validated; uploads are checked by type, content and size (5 MB).

6. The main modules and their APIs

ModuleKey APIsHow it works
EmployeesGET/POST /employees, PUT /employees/{id}, /deactivate, /salary, /documents Onboarding creates the login account, profile, salary structure and leave balances in one step, then emails a welcome message. Deactivation is a soft delete: login is blocked and history is kept.
Attendance/attendance/check-in, /check-out, /me, /daily, /summary, /override 8+ hours = present, 4+ hours = half day, less = absent. HR can correct any day with a reason (audited). A monthly summary shows present, absent, leave, late and hours.
LeavePOST /leaves, /preview, /{id}/approve, /reject, /cancel, /balances/me Counts only working days (no weekends or holidays). On approval, days are taken from the balance; extra days become Loss of Pay (LOP). Overlaps and self-approval are blocked.
PayrollPOST /payroll/runs, /{id}/lock, /{id}/credit, /payslips/{id}/adjustments Draft → Locked → Paid. Salary is calculated from attendance + leave. HR can add bonuses or deductions in draft. Locking freezes that month and creates PDF payslips; "credit" simulates the bank transfer.
PayslipsGET /payroll/payslips/me, /payslips/{id}/pdf A ReportLab PDF with employee details, earnings, deductions and net pay in words. Employees download only their own; Admin sees all.
Notifications/email-templates, /email-logs, /notifications Emails for onboarding, leave, payslip and payroll use editable templates. Every email is logged; it is sent via SMTP when configured.
Reports/reports/attendance, /leave, /payroll + ?format=csv|pdf Filter by date range and department, view on screen, export to CSV or PDF.
Admin & audit/roles, /users/{id}/role, /audit-logs, /dashboard/admin Role and permission management, organisation settings, and a read-only audit log of every critical action (who, what, when, IP, before/after).

7. Payroll formula (simple version)

Per-day salary = monthly gross ÷ working days in the month.   LOP deduction = per-day salary × LOP days (absent days without leave + unpaid leave).
Net salary = gross earnings + bonuses − (LOP + Provident Fund 12% of basic + Professional Tax ₹200 + TDS + other deductions). New joiners and leavers are paid only for the days they were employed in that month.

8. Frontend: how the screens work

  • AuthContext remembers the logged-in user and their permissions. can('payroll:view') decides which menus and buttons appear.
  • api/client.js (Axios) adds the token to every call and refreshes it automatically on expiry.
  • React Query hooks (useApi, useAction) load data, show spinners, display success/error messages and refresh lists after changes.
  • Admin panel: dashboard charts, employees, attendance board, leave approvals, payroll, reports, roles, email center, audit logs, settings.
  • Employee panel: check-in/out, attendance calendar, apply and track leave, payslip download, profile and documents.
  • The Vite dev server forwards /api to the backend (port 8000); the UI runs on port 5173.

9. Data safety and testing

  • Each action runs as one database transaction: the change, its audit entry and its email are saved together or not at all.
  • Locked payroll months cannot be changed (the API returns HTTP 423). Payslips keep a snapshot of employee details.
  • 29 automated tests check login, permissions, duplicate check-in, leave/LOP, payroll maths, locking, file upload safety and the audit log.
